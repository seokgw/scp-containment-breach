# ACT II–IV 확장 계획

**011–040은 현재 전부 미구현**입니다. UI에는 ACT 단위의 planned 카드만 있고 개별 문제·컨테이너·정답 API를 등록하지 않았습니다.

| 구간 | 내부 상대 난이도 | 주제와 스토리 |
|---|---|---|
| 011–015 | 3–4/10 | SCP-079 접속 흔적, 세션·인증·기초 IDOR 심화 |
| 016–020 | 4–5/10 | SQLi·XSS·HTTP 분석·리버싱 입문, 제한 변경 경로 |
| 021–025 | 5–6/10 | 내부자 권한·Linux 권한 상승·네트워크 포렌식 |
| 026–030 | 6–7/10 | 메모리·로그 조작·암호학·복합 침해 경로 |
| 031–035 | 7–8/10 | O5 비밀 명령·다단계 분석·고급 리버싱 |
| 036–040 | 8–10/10 | 전체 증거 재구성·최종 선택, PROJECT BLACK VEIL |

보안 인가 LEVEL 4·5는 새 챕터의 명시된 unlock 조건으로 확장합니다. 현재 기본 로직은 연속 완료 챕터 수를 인가로 계산합니다. 추가 챕터의 인가가 챕터 번호와 1:1이 아닐 때는 chapter 모델에 `awardedClearance`와 조건 평가 함수를 추가하고 기존 001–010의 결과가 바뀌지 않는 회귀 테스트를 유지합니다.

## 새 문제 등록

1. 출제 문서에서 선수 지식, 분석 경로, 배점, 난이도, FLAG 도출 방식, 스토리 공개 범위를 정합니다.
2. `backend/catalog.mjs`에 chapter·challenge, requiredClearance, releaseStatus, 실제 자료 경로, 세 단계 힌트, 해결 후 해설·문서를 등록합니다. 번호만 있는 빈 문제를 released로 두지 않습니다.
3. `public/evidence/<번호>/` 또는 독립 lab 폴더에 가상 자료를 추가합니다. 실제 계정·개인 데이터·내부 네트워크 정보를 쓰지 않습니다.
4. 정답의 SHA-256 검증 해시를 서버 전용 `backend/verifiers.json`에 등록합니다. 원문 정답 목록은 무시된 출제자 보관 폴더에 둡니다. 공개 자료에 정답 단서가 포함되는 것은 문제 목적에 맞는 경우에만 허용합니다.
5. Supabase migration으로 chapters/challenges 메타데이터를 동기화합니다. SQL 파일은 `supabase migration new <name>`으로 만들고 검토합니다. 정답 원문을 DB migration에 넣지 않습니다.
6. 독립 풀이 테스트로 자료→분석→FLAG→채점→문서→인가를 검증합니다. 새 문제의 잠금 조건과 기존 풀이·랭킹 호환성을 확인합니다.
7. 준비 중 상태에서 검토하고, 실제 lab·자료가 준비된 후 released로 바꿉니다. Edge 함수와 Vercel을 같은 버전으로 배포합니다.

현재 `progressOf` 완료 기준(10문제), UI 분모(10, 2,250), solved-chip 및 엔딩은 ACT I에 맞춘 값입니다. ACT II 출시 시 전역 하드코딩을 늘리지 말고 ACT별 카탈로그 집계로 옮겨 ACT I의 10문제 완료 상태를 독립적으로 유지해야 합니다. 데이터·저장소·채점 구조는 재사용하되 이러한 MVP 표시 상수는 변경 대상입니다.

## 실습 컨테이너 추가

독립 Dockerfile과 가상 fixture를 만들고 새 서비스에 UID 1000, read_only, cap_drop ALL, no-new-privileges, internal network, CPU·메모리·PID 제한을 적용합니다. 호스트 포트는 127.0.0.1에만 바인딩합니다. 운영 DB·세션·키·Docker socket·호스트 파일은 마운트하지 않습니다. 문제별 서버에는 필요한 읽기·쓰기 범위만 제공합니다.

공개 브라우저 원격 실습을 향후 제공하려면 별도의 격리 실행 호스트, 이용자별 인스턴스·TTL·정리·네트워크 정책이 필요합니다. 현재 Vercel 운영 API에 의도적 취약점을 추가하는 방식으로 대체하지 않습니다. 이 MVP는 그러한 원격 컨테이너 인프라를 구축한 것으로 주장하지 않습니다.
